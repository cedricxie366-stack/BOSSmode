# BOSSmode 本地预览版

原名 Builder Mode。为兼容已有安装和项目，安装标识 `builder-mode`、工具名和 `.builder-mode` 记录目录保持不变。主仓库见 https://github.com/cedricxie366-stack/BOSSmode 。

让普通创作者与一个持续负责的伙伴讨论目标、保存产品约定、实施修改和检查结果。此目录是 Codex 安装入口和共享核心；DSH 用户通过源码根目录的原生 bundle 安装，步骤见根 README。两种宿主不必同时运行，均无需自建 builder-web。真实用户已提出首轮反馈，修复后复试尚未完成，不能宣称已验证通用专业团队效果。

核心体验是：你负责目标、体验和判断，负责人负责技术与协调。你可以直接问“现在能体验什么、下一步会带来什么效果”；真正需要你决定时，应先得到选项、影响和建议，而不是技术问卷。普通问题由负责人自行处理，危险或未知结果不会被隐瞒。

新项目会先和你对齐第一版：能得到什么、在哪里使用、先做与暂不做什么、接下来按什么顺序推进。你认可后才进入制作，之后不为普通小修改反复确认。选择“用某个AI服务”或提供凭据，不等于认可整套方案。换任务后仍记得方案回应；已有项目资料不会被清空。

每次说明先讲对你的使用意味着什么。例如电脑上试过，不会说成手机微信也已能用；需要放到网上时，先解释访问保护、费用及哪些尚未确认。听不懂时直接指出即可，不需要自己查术语。

`0.2.0-preview.3` 新增发送前表达检查：负责人须把进展、提问和最终答复的实际草稿交给检查工具，发现已识别的黑话、未解释术语或过量技术细节时先改写。默认用通俗表达；你明确说自己熟悉某类技术后，才在相关范围内增加少量细节。说“还是简单一点”即可恢复通俗表达，换对话后仍能读取项目内保存的偏好，不影响项目方案或操作权限。

检查在本机运行，不额外调用付费模型、不上传草稿，也不保存整份回复。它结合已知表达规则和负责人的语义自查，不是独立事实认证；没有统一拦截宿主全部显示渠道的能力。因此这是要求先审后发的工作流程，不承诺任何情况下都能阻止未审查文字显示。默认不反复展示“审查通过”的标签。检查失效时不能伪造通过结果。

项目采用 Apache License 2.0，见源码根目录或运行包中的 LICENSE。当前是开源预览版；安装插件不会自动公开你的项目。

## 开始使用

已安装后，请在 Codex 新任务中选择一个独立产品文件夹，启用 BOSSmode，然后说：“我想做……，先和我讨论，不要马上开发。”确认方向后说：“按照这个方向实施。”继续旧项目时说：“读取这个文件夹的 BOSSmode 项目状态，告诉我进展并继续。”旧的 Builder Mode 称呼仍可识别。

插件更新后建议新任务确保加载完整的新规则；已有对话可能保留旧技能内容，即使工具列表已刷新。产品文件默认放在 product，记忆放在 .builder-mode。不要把插件源码目录当作产品目录。

不要让旧版任务和新版任务同时写同一个产品目录。新版协调锁覆盖新版插件的修改、验收与备份；跨旧版并发操作不在已验证支持范围。

当前验证环境：macOS arm64、Node.js 24、Codex CLI 0.154.0。其他系统尚未完成运行验收。报名应用检查依赖 macOS Seatbelt；不支持时应失败关闭，不能假装检查通过。

## 能做什么

- 保存目标、用户决定、假设、开放问题、研究来源和规则；新任务恢复，不依赖复制聊天。
- 负责人简报保存当前重点、预期效果、风险和下一检查点，结果引用重新核对当前成果；没有依据时不报完成百分比、工期或费用。
- 首次制作有方案对齐检查；没有保存明确的产品方案回应时，插件不启动新的变更。该回应仍是助手有来源的转述，不是防伪的人类认证，也不授予外部权限；宿主原生工具的行为仍依赖技能与权限约束。
- 简报区分已登记的工作与实际执行状态；没有宿主证明时，不把保存的“运行中”说成仍在工作。未知动作、缺失证据及旧版未决事项会明确提示，负责人先核对而不让用户重述背景。
- 决策说明包含两到三个业务选项及影响、建议；用户选择只能作为有来源的转述，不会自动变成付费/发布授权。
- 在 Codex 原生能力允许时安排具体专业子任务，主线程收取和整合；不要求用户搬运结果。
- 报名样例支持基础报名、先进先出候补、持久化、备份恢复的独立业务检查。
- 研究笔记、内容稿和其他文件成果支持检查。通用检查可按项目冻结文件、文本、JSON 字段要求；不执行候选代码，不把结构齐全当作事实/质量合格。
- 可按具体成果版本记录 AI 评审或转述用户反馈，生成带成果副本、检查报告、评审意见和未决项的本地交付包。内容改变、报告篡改或约定变化后，旧评审不能沿用；模型不能代替用户授予批准。
- 展示交付时再次检查包内文件和最新评审；新的修改意见或文件损坏会使旧包退出“当前有效结果”，历史文件仍保留。
- 项目累计尝试次数仅记录用量，不自动停工；同类任务自动修复最多两次，须提供新诊断。费用不可见时标记未知。

## 恢复与安全边界

可要求“备份项目状态”或“从指定备份恢复到新目录”。新版 v2 备份包括主状态库、动作/验收日志、已检查的成果快照、报告和本地交付包，并校验文件摘要。恢复永不覆盖原状态，提升负责人版本、保留去重与未知结果、清除可复用批准。报告正文保留历史路径，状态中的报告位置映射到恢复副本。

运行中的业务数据库和当前工作代码不属于此备份；恢复副本不自动运行产品。旧 v1 备份仍可恢复，但明确缺少日志与成果。需要继续修改时，从已检查快照/交付包取回所需成果到独立 product 目录，重新检查，不能把恢复记录当作当前运行环境已验收。备份只支持本地有界资产，不是通用整机备份。

状态升级前会保存原数据库副本；不自动降级更新版本的数据库。迁移副本用于恢复原版本环境，不应直接覆盖正在使用的数据库。当前保存负责人沟通的版本为 schema 5，旧项目由插件打开时迁移并保留原副本。

执行者停止状态不明时保持阻断，不自动重派。当前没有原生停止凭据的自动接入。外部动作工具只记录和检查提案，不执行发送、支付或公开发布，不授予权限。真实客户数据不在此候选版验证范围内。报名页面的取消确认不是组织者身份授权，不能直接公开接收真实报名。

验证隔离有明确范围，不是抵御任意恶意宿主进程的完整系统沙箱。桌面主线程委派已验证，非交互 CLI 插件内委派曾失败，不能承诺二者等效。

## 停用和问题排查

在 Codex 插件界面停用或卸载插件，不需要删除产品目录或 .builder-mode；保留它们以便重新安装后恢复。插件没有自动删除用户项目的卸载程序。不要为了排错清空状态库。

出现版本冲突先重新读取项目状态；出现未知执行者先检查恢复状态；结构检查失败修正对应文件；待评审不是失败也不是已交付。数据库损坏时保留原文件，恢复到新目录。遇到费用、权限、真实数据或重要方向选择才交由用户决定。

交付状态解释：needs_review 表示仍缺实质评审；reviewed_candidate 表示已记录相应评审、仍是候选；accepted_profile_scope 只表示固定业务检查范围通过。以上都不等于公开发布、生产级保证或宿主证明的用户认可。

runtime 已随包提供，正常运行无需开发仓库。scripts/sync-core.mjs 和 test 仅供源码仓库开发，不是用户安装步骤。本包不自动上架你的成果、不额外安装依赖。
